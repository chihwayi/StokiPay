## Scope delivered

- `products`, `stock_movements` (append-only, `UNIQUE(tenant_id, operation_id)` idempotency per ADR 0003), `exchange_rates` (ADR 0004), `stock_counts`/`stock_count_lines`, and a `stock_levels` view (`security_invoker`, derived from movements only — never an independently-writable total).
- RLS: any tenant staff can log a receipt/adjustment for themselves on their own registered device; only owner/manager can create/edit products or approve exchange rates (the "rate role"); reason required for adjustments via CHECK constraint.
- `stockflow_submit_stock_count`/`stockflow_approve_stock_count` (SECURITY DEFINER) implement genuinely blind counts — the counter can never see or set `expected_quantity` (RLS-enforced, not just a UI convention), and a variance only becomes a stock movement after owner/manager approval.
- UI: `/products`, `/products/new`, inline receive/adjust forms, `/counts` → `/counts/new` → `/counts/[id]` (blind entry → submit → owner/manager review → approve).
- 34 integration tests (`tests/integration/{rls,stock}.test.ts`) covering reconciliation, idempotent replay, reason-required adjustments, device/actor spoofing denial, rate-role denial, and the full blind-count flow.
- Verified live end-to-end via the real Kong/PostgREST endpoint (not just direct Postgres): onboarded a tenant, created a product, registered a device, received stock, confirmed `stock_levels` reconciled — then cleaned up.

## PowerSync — root cause found and fixed

The crash-loop (`Fatal startup error - exiting with code 150. postgres query failed`, thrown from `PostgresLockManager.init()`'s `CREATE TABLE IF NOT EXISTS locks (...)`) was **two real, independent Postgres-side bugs**, not a PowerSync bug — found by copying the actual image contents to a writable debug location, patching in a one-line `console.error` to dump the normalized connection config, and running the real `service/lib/entry.js start -r unified` entrypoint directly (rather than continuing to speculate from swallowed generic errors — PowerSync's own error wrapping discards the real Postgres error text for connection-phase failures, which is what made this misleading for so long):

1. **`sslmode` was never being set for the storage connection.** `infra/powersync/config.yaml`'s `replication:` block had `sslmode: disable` but the `storage:` block didn't. PowerSync's config schema (`libs/lib-postgres/dist/types/types.js`, `BasePostgresConnectionConfig`) defaults `sslmode` to `verify-full` when omitted, and explicitly does **not** read it from the connection URI's query string ("Configuration not supported via URI" — confirmed by reading the actual normalization code). So the storage role's very first query attempted a TLS handshake against a Postgres with no server certificate configured, and failed. Fixed by adding `sslmode: disable` under `storage:` too (now committed).
2. **The storage schema name PowerSync creates is hardcoded, and didn't match what Sprint 2 had provisioned.** `modules/module-postgres-storage/dist/utils/db.js` hardcodes `STORAGE_SCHEMA_NAME = 'powersync'` — this is **not configurable** via `config.yaml`. Sprint 2 had created and granted a schema named `powersync_storage` instead (a reasonable-looking but wrong guess at the name). `powersync_storage_role` has only `CONNECT` on the `postgres` database, not `CREATE`, so `CREATE SCHEMA IF NOT EXISTS powersync` failed with `permission denied for database postgres` — which is Postgres's real (and correct) error for "you can't create a new top-level schema here," but PowerSync's generic error-wrapping for connection/init-phase failures discarded that message before it ever reached the logs. Fixed by creating the schema literally named `powersync` (see `infra/powersync/setup.sql`, added this session) and granting `powersync_storage_role` full rights on it — same least-privilege shape as before, just the correct name.
3. **A third, smaller issue surfaced once the above two were fixed:** PowerSync's replication connection also needs `BYPASSRLS` — it reads raw committed changes outside any per-request JWT/session context, so it cannot satisfy our tenant-scoped RLS policies and was only seeing 0 rows per table (logged as `PSYNC_S1145` warnings). Tenant scoping for what a *client* actually receives is enforced separately by `sync_rules.yaml`, not by RLS, so this doesn't weaken tenant isolation for app data — RLS/PostgREST is still the boundary for every ordinary client request. Fixed with `ALTER ROLE powersync_role BYPASSRLS;`.

All three fixes are now applied on staging and captured in `infra/powersync/setup.sql` (new, idempotent) for reproducibility on any future environment. The service (Coolify application `stockflow-zw-powersync`, uuid `idbsgh31p9tdpa2pkx3c434n`) is running, has created its replication slot, and is actively replicating `tenants`, `branches`, `staff_users`, `devices`, `products`, `stock_movements` — confirmed via `/probes/liveness` returning `200` and container uptime holding without restarts.

**Operational note carried forward from gotcha #10:** every Coolify restart/redeploy of this application disconnects it from the Supabase service's Docker network (manually-attached networks don't survive `docker restart`) — after any redeploy, `docker stop` + `docker network connect o11niv82f82abmmfm95kvy76 <new-container-name>` + `docker start` is required, or it will crash-loop again for the unrelated reason of not being able to reach `supabase-db` at all (a different failure mode than the two above, but produces the same generic "postgres query failed" message, which cost real time re-diagnosing during this session before the network was checked).
